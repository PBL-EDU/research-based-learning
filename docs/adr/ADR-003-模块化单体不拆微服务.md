# ADR-003：模块化单体，不拆微服务

## Status
Accepted（2026-11-13）

## Context
系统只有三类功能域（发布、讨论、目录浏览），部署规模预计从 30 人涨到几百人，维护者 1–3 人且可能逐年轮换（学生社团/课程项目）。但需求中"三端"很容易被误读成"三个服务"。

## Decision
服务器为**单个 NestJS 进程**，内部按 bounded context 分模块，模块间只能通过 application service 调用，不能跨模块直接读对方的表：

```
identity ──┐
template ──┤
publication ┼─→ engagement ─→ notification
asset ─────┤
moderation ┘
portal-read（只读聚合，只依赖其他模块的公开查询）
```

每个模块内部四层：`http → application → domain → infra`，依赖只能向内。用 CI 脚本禁止 `domain/` 目录 import `nestjs`、`prisma`、`@aws-sdk/*`。

## Consequences
**变容易**
- 一次事务可以同时写 publication 与计数，讨论区不会出现"评论数对不上"的经典分布式问题；
- 部署是一台机器、一个 compose 文件、一条命令；
- 学生接手时，"目录即边界"，不需要理解服务发现与 RPC。

**变难**
- 无法按模块独立扩容（接受：瓶颈在图片与渲染，已用 worker 隔离）；
- 未来若要拆，得先抽掉跨模块事务（已预留：所有跨模块写入都经过 application service，没有散落的 JOIN）。

## 明确的拆出点（仅两处，且必须等到有真实压力才动）
1. `asset`（图片转码 + CDN）——CPU/带宽特性独立；
2. `ai-gateway`（若未来改为平台代付大模型）——配额与审计独立。

## Alternatives considered
| 方案 | 否决理由 |
|---|---|
| 微服务（publication / engagement / asset 三个服务） | 为 3 个模块引入服务发现、分布式事务、链路追踪，运维成本超过收益 |
| Serverless（Vercel + Supabase） | 图片处理与 mermaid 渲染需要常驻 worker；国内访问与合规不可控 |
| BaaS（Firebase/Supabase 直连） | 权限模型难以表达"作者才能撤回、仅 published 可见"，且门户会绕过后端 |
